Why residencyR

Built to be trusted on infrastructure you can't risk.

Every claim below is something we tested, not something we assumed.

0

Zero-dependency audit engine

Scanning, classification, and ingestion run on base R — grDevices, graphics, utils. Nothing else to install to run an audit. Certificate generation is commercially licensed and additionally requires openssl for signature verification.

⌁

Runs fully offline

No network calls, no live database connections, no API credentials. Point it at a CSV on an air-gapped laptop and it works exactly the same.

⚡

Fast at real scale

A full audit — ingest, scan, flag, PDF with charts — completes in about a second on 5,000 assets, far beyond any single institution's realistic inventory.

＋

Extensible by design

New data sources register themselves into a shared dispatch registry. Adding a fifth source never means touching the first four.

?

Honest about uncertainty

Mixed signals classify as "unknown", never an automatic pass. Scanner failures surface on the certificate itself — never a silently smaller audit.

§

Regulator-agnostic

The regulatory citation and deadline are parameters, not assumptions baked into the code. Built for CBN 2027 — not limited to it.

Jurisdiction classification is deliberately conservative. A row matching both a local and an offshore signature — a genuinely ambiguous case — resolves to unknown, never an automatic pass. Getting your data in

Three paths, in order of how much trust each deserves.

Send this to your engineering team

The exact request that gets you a usable file back on the first try.

Dear Engineering Team,
To run the Infosights Data Residency Readiness Scan, please provide a masked CSV file containing data from the following four specific infrastructure sources:

  1. Core Databases (db): An inventory list of all production and staging database instances, including hosting cloud regions or physical data center zones.
  2. System Backups (backups): A list of all active storage buckets, cold archives, and snapshot destinations used for disaster recovery.
  3. API Gateways (api_logs): A 24-hour log summary showing outward-facing connection endpoints and routing targets.
  4. Third-Party Vendors (third_party_calls): A connection log of external webhooks, identity verification platforms, and international payment processors connected to your ecosystem.
Data hygiene & masking protocol For security and data privacy compliance, your engineering team should completely sanitize and mask these files before sending them. Redact all internal passwords, cryptographic keys, and customer-identifying data. We only require the structural system names, target URLs, destination IPs, and hosting regions to evaluate CBN compliance alignment.

3

Raw code scanning — candidate findings only

If an engineer hands you a Terraform/config repo instead of a CSV, scan it directly for provider/region signatures.

candidates <- scan_source_files("path/to/repo")
Read this before a client demo: every row is tagged confidence = "candidate" and is never registered as an audit source — it can't silently blend into a certified result. Treat it as "worth checking," not "confirmed."

Interpreting results

Three verdicts. No ambiguity about what they mean.

COMPLIANT

No offshore or unknown items found in this audit.

NON-COMPLIANT

At least one flagged item — see the remediation list.

UNKNOWN

No data was audited — check your config before trusting this result.

Limitations, stated plainly

The parts that still need a human.

A tool that hides its own rough edges is the fastest way to get contradicted in a live demo.

＊

Accuracy depends on input quality

The tool classifies whatever provider/region text it's given. There is no independent verification against actual cloud infrastructure.

＊

The code scanner is a heuristic, not an audit

It's for triage before building a real CSV inventory — not a certification source.

＊

No live cloud API integration, by design

This is what makes the "runs on an air-gapped laptop" claim true. It also means residencyR never confirms your data reflects current reality — that's on your process.

＊

Terraform state (.tfstate) parsing isn't built

Plain-text .tf files are supported today; .tfstate is JSON and would require a dependency that hasn't been added.

＊

Indicator lists aren't exhaustive

Local and offshore provider signatures are a working set, verified as they're added — not a complete registry of every provider that exists.
